# 智能路由的 Responses 请求

智能路由接受 `POST /v1/responses` 和 `POST /responses`。入口采用原生协议优先的转发方式，沿用现有模型顺序、账号凭据刷新、请求预算和健康状态；打开页面不会探测接口、启动登录或查询额度。

## 来源与转发方式

| 来源                 | 行为                                                                                                                                                                           |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 普通 API 模型        | 实际请求先发送到 `/responses`，保留原始字段，仅替换为所选上游模型。基础地址已经包含 `/responses` 时不重复追加；包含 `/chat/completions` 时替换末尾路径。                       |
| ChatGPT / Codex 账号 | 使用账号原生 Responses 接口。遵守上游要求，使用流式传输和 `store: false`；按需补充默认 instructions 与 encrypted reasoning include。调用方请求非流式时，收集真实终态响应对象。 |
| GitHub Copilot 账号  | 已保存的模型协议明确为 Responses 时直接使用；其他情况依据模型目录的 `supported_endpoints` 判断。支持多个协议时，Responses 请求优先使用 Responses，不发送额外推理探针。         |
| 其他已接入账号       | 复用现有 Chat 适配，再转换为 Responses 输出；无法转换的输入明确报错或跳过该候选，不丢弃工具能力。                                                                              |

原生 JSON 保留上游完整响应对象，包括真实 ID、reasoning、annotations、usage 和扩展字段。原生 SSE 保留事件字节、未知事件和注释；监测完成或失败不重建正常事件。去除连接、编码及敏感凭据响应头，保留适用的错误与限流元数据。

原生请求明确返回不支持端点或该模型不支持 Responses 时，才尝试兼容 Chat 转换。真实参数错误、策略拒绝、模型不存在、认证失败和限流不会触发同一请求的协议重发。已确认不支持的来源在运行时缓存 5 分钟，最多 128 项；配置指纹改变后不复用旧判断。转换与转发共用原请求的时间预算。

Chat 转换覆盖已有消息、函数调用、工具结果和支持的 reasoning 输入。仅原生协议能够承载的托管工具等字段不会被静默删掉。兼容转换生成的响应 ID 不具备上游保存状态，下一轮须发送完整输入。

## 续接与失败

成功的原生 `completed` 或 `incomplete` 响应将真实 ID 绑定到原候选及其配置指纹。绑定在现有路由记忆中保存，最多 512 项、有效期 24 小时，仅保存 ID、来源指纹、期限及冲突标记，不保存对话内容或凭据。

带 `previous_response_id` 的请求只发送给原来源，不会因优先级变化、限流或认证错误切换账号。未知、过期、冲突或配置已改变的 ID 在请求前返回错误；调用方可以改为完整输入开启新请求。不同来源返回重复 ID 时，该 ID 标记为冲突，不能继续绑定到任何一方。

上游决定响应是否可以继续使用；本机绑定不会创造服务端状态，`store: false` 的账号接口仍受其自身续接政策约束。原生 Responses 的会话语义依据 [官方会话状态说明](https://developers.openai.com/api/docs/guides/conversation-state)。

`response.failed`、`error` 和非流式失败对象保留真实错误信息，按认证、限流、计费、模型或临时故障分类。明确的续接 ID 错误仅影响该次续接，不将整个模型置入冷却；认证或限流错误仍按现有规则处理。收到合法完成事件才记为成功；畸形终态、截断或缺失终态不会生成成功响应。取消会释放上游请求和活动计数，已交付流内容后不重放请求。
